# Keep your observatory up to date

You can maintain the website with the free Pages CMS dashboard. Astro and GitHub Pages still build and host the website; the dashboard only edits files in this GitHub repository. No terminal, paid service, database, or extra website hosting is needed.

## Connect Pages CMS once

1. After this integration PR is reviewed, passes all checks, and is merged, open [the free hosted Pages CMS dashboard](https://app.pagescms.org).
2. Choose **Sign in with GitHub** using the account that can write to `simjiahui/simjiahui.github.io`.
3. Follow GitHub's prompt to install/authorize the **Pages CMS GitHub App**. Select **Only select repositories**, then choose **simjiahui.github.io**. Organization-owned repositories may require an owner's approval.
4. Review the permissions shown by GitHub. Editing requires repository Contents read/write and Metadata read access. The current official app documentation also lists Administration and Actions read/write, Checks and Commit statuses read access, and account Email addresses read access; the hosted installation screen is authoritative. Limit the installation to this repository. These permissions let the app edit repository files and observe checks; they do not move your hosting.
5. Open this repository in Pages CMS. The `.pages.yml` configuration is already supplied; do not replace it with an example or create another configuration.
6. In GitHub repository **Settings → Pages**, keep **Source: GitHub Actions**. Leave the existing Astro deployment workflow in place.
7. To prevent accidental direct publishing, set a `main` branch rule/ruleset requiring a pull request and the **build** status check before merging. Do not grant the CMS a bypass. Repository administrators configure this once in GitHub; `.pages.yml` cannot enforce branch protection.

You do **not** need to create your own GitHub App, copy a token, enter a password into a file, install a database, or deploy a CMS server. The hosted app supplies the dashboard and its own authentication. You can revoke its repository access later through GitHub's **Settings → Applications → Installed GitHub Apps**.

## The everyday dashboard workflow

1. On GitHub, create a small working branch from the latest `main`, for example `content/new-journal-entry`.
2. In Pages CMS, select that branch with the repository's branch selector **before editing or uploading**. The configuration must exist on the selected branch. The dashboard saves commits to the selected branch; it does not automatically open a PR or guarantee validation by Astro.
3. Open one of the editors in the table below, make your changes, and save. Keep the same branch selected when making related media and text edits. Saving a journal with **Draft** enabled is different from saving a Git branch: Draft hides the post on the website, but its source is still visible in a public GitHub repository.
4. Open a pull request from that branch to `main` on GitHub. Review the changed files. A generated `projects.json` may be regenerated by the workflow from the project editor file; do not edit it separately.
5. Wait for **Check & deploy Moonlit Tides → build** to pass. It validates the content, CV, links, CMS save compatibility, and browser behavior. Review the browser screenshots attached to the run. Fix any error in the same branch rather than merging a failing PR.
6. Merge only after review and passing checks. The `main` run builds and deploys to the existing GitHub Pages site. Wait for its **deploy** job to succeed; a successful PR check does not deploy. If you still see an older heading, check the main run before refreshing the website.

Do not edit `main` directly in the dashboard: a save there can immediately trigger deployment. Branch protection is the server-side safeguard; this guide and the CMS configuration do not replace it.

## Headings, line breaks, and italics

Website headings and subtitles intentionally use plain single-line or multiline controls, not an HTML rich-text editor. In the dashboard:

- Press **Enter** in a multiline field for a real line break. Do not type the two characters `\n`; those are only needed when editing JSON manually.
- Write `*words*` for italic emphasis. Keep the pair of asterisks on the same line. For example, enter `Dynamical systems.`, press Enter, then enter `*Reservoir computing.*` to retain the current two-line appearance.
- Keep tokens such as `{name}`, `{institution}`, `{count}`, and `{percent}` exactly spelled. Edit the surrounding wording freely. Do not paste HTML.

The dashboard writes the newline and asterisks into the existing string fields. The existing safe renderer still produces text, line breaks, and emphasis; no template or CSS redesign is involved. Astronomy coordinates and scientific reference templates are intentionally outside these editing controls.

## Add photographs

1. Choose **Photographs and media** and upload a JPG, PNG, WebP, GIF or SVG. Prefer small, descriptive filenames; the CMS makes names URL-safe. Upload only trusted SVG files.
2. Open the relevant **Portrait photograph**, **Project image**, **Cover photograph**, or gallery **Photograph** picker and select the uploaded file. Uploading alone does not insert it into a page.
3. Add alternative text describing the picture. The portrait alternative text is in **About Me and biography → Shared → Portrait Alt**; each gallery and article cover has its own field.
4. Save on the same working branch. URLs must look like `/images/my-photo.jpg`, not `public/images/my-photo.jpg`. An empty portrait/gallery image retains the existing placeholder behavior.

Before deleting or renaming an uploaded file, remove/update all references to it. The build checks local links and images.

## Publish a journal article

1. On your working branch, open **Journal / blog articles** and create an entry. Enter the title, short summary, publication date, and one of the four category options. The date picker stores `YYYY-MM-DD`; the website's existing UTC+8 date handling is unchanged.
2. Add tags and an optional cover with alternative text. Leave **Draft** on while writing. Leave **Sample** off for real writing; the existing demonstrations keep Sample on.
3. Use the **Article body → Editor** toolbar for headings, paragraphs, emphasis, lists, links, and images. The output is Markdown below YAML frontmatter in the same `.md` format Astro already reads.
4. For equations (`$...$` / `$$...$$`), fenced code, or unusual Markdown, switch to **Source before editing the body**. The visual editor does not guarantee a lossless round trip for all LaTeX/Markdown extensions. Keep technical articles in Source mode and inspect the diff; do not convert existing mathematical articles through visual mode. Editing only frontmatter does not require changing the body.
5. Use a stable, lowercase filename with hyphens, such as `my-new-research-note.md`. It determines the article URL. Renaming and deleting articles are disabled in the dashboard to protect existing links; mark an entry Draft to withdraw it.
6. When ready, switch **Draft** off, save, open/review the PR, and merge after checks pass. Drafts are excluded from the homepage, journal list, article routes, and RSS. New public articles appear in those places after the main deployment succeeds.

## Publications, projects, and the automatic CV

Use the academic editor's date picker and publication-type dropdown. Add authors in their desired order. Keep publication and project IDs unique, lowercase, and hyphenated; preserve IDs already referenced by a project. A project's related-publication field uses that publication's ID, not its title or URL. Cross-file relationships and exact calendar dates are validated by the build, since the hosted CMS cannot run Astro's validators before every save.

**Placeholder** means sample/unverified data; it excludes a publication from the CV. Turn it off only for verified records. **Featured** controls homepage placement. Education/experience dates stay text because they support years and `Present`, not just calendar dates. The existing PDF CV is regenerated automatically from the same academic/profile data on every build; no separate CV editor or subscription is needed.

### Compatibility details — keep these conventions

Pages CMS 2.x removes blank strings, null values and empty lists before saving. The website supplies narrowly scoped defaults for already-optional blank values/lists (empty biography note, email, portrait, gallery captions, academic lists and optional project links). Required identity, publication, category and heading validation remains active. Most nonempty copy fields are required by the editor; keep meaningful text in them. Unknown keys and invalid data still fail website checks.

The current CMS serializer also writes an empty top-level array as an empty file. To avoid invalid JSON when you remove the final project, **`src/data/projects.cms.json` is the authoritative object-shaped editor**: `{ "projects": [...] }`. The website validates that source and retains the original array shape for its consumers. `npm run content:prepare` generates `src/data/projects.json` before development, validation and CV/build commands. An empty editor object becomes a valid `[]` output. Do not hand-edit the generated array; change the Featured GitHub projects editor (or the wrapper file for manual maintenance). No other existing content file has been migrated or restructured.

The existing journal articles have an explicit `draft: false` added to their frontmatter. This preserves their published status when first opened in the dashboard, even though newly created CMS articles default to Draft on. Their Markdown bodies and other frontmatter values are unchanged.

Neither `.pages.yml` nor the hosted CMS can enforce cross-file publication IDs, protect Markdown extensions in visual mode, install branch rules, or replace Astro/CI validation. Required PR checks are the publication gate. No CMS editor exposes `src/data/referenceLocation.json`; astronomical calculations, the fixed Asia/Shanghai calendar, and the tidal renderer are unchanged.

### Line breaks and italics, without HTML

Headings and static paragraphs support two simple conventions:

- Type `\n` inside a JSON string to insert a line break. Keep the string on one line in the file; do not press Enter inside its quotation marks.
- Put one asterisk on each side of words for italic emphasis: `*these words*`.

For example, the homepage introduction heading is:

```json
"heading": "Curiosity at the edge\nof *complexity.*"
```

It displays as “Curiosity at the edge” on the first line, then “of complexity.” with “complexity.” italicized on the next. You can change it to:

```json
"heading": "Questions about\n*learning and dynamics.*"
```

Use `*single asterisks*`, not double asterisks, and keep each italic phrase on one side of a line break. HTML tags such as `<br>` or `<em>` are not needed; they display as ordinary text. Metadata, counts, and plain dropdown labels remain plain text, so use ordinary wording there. If you need a quotation mark inside a sentence, write `\"` in the JSON string.

### Keep automatic values and relationships intact

Some wording contains values such as `{name}`, `{role}`, `{institution}`, `{percent}`, or `{count}`. Keep those tokens spelled exactly as shown: the website fills them from your profile, astronomical calculations, or filtered records. Edit the surrounding words freely. For example, `"{count} records"` can become `"{count} research entries"`.

In `research.themes`, edit titles/descriptions/captions freely, but keep each `id` stable so related publications and project links continue to work. Equations use the existing LaTeX `math` field, with backslashes escaped for JSON; changing mathematical notation does not require an Astro component edit. In `journal.categories`, edit `label` to change what visitors see, and keep `value` unchanged so article categories and filters still match.

Edit `src/data/referenceLocation.json` to change the astronomical reference observer: `name`, decimal-degree `latitude` (north positive), `longitude` (east positive), and `elevation` in metres. This single configuration supplies the lunar coordinates, tidal geometry, homepage coordinates, observation notes, and colophon. Keep `{referenceName}`, `{referenceLatitude}`, `{referenceLongitude}`, and `{referenceElevation}` intact in the explanatory copy; the website fills them automatically. The personal location in `profile.json` is independent. The Chinese lunisolar calendar stays fixed to `Asia/Shanghai` (UTC+8), regardless of the reference observer or visitor timezone.

The configuration is validated during every build. Missing keys, misspelled placeholders, invalid types, and duplicate theme/category identifiers fail the checks with a field path. If checks fail after an edit, fix the indicated field in the same branch. No part of the new wording is published until the build passes and the pull request is merged.

Two optional messages can be removed or set to `""`: `hero.observation.explanationLink` hides the link beside the lunar observation note, and `home.contact.missingEmail` hides the missing-email notice. Keep other required keys intact.

## 1. Add a publication once, update the site and CV

Open `src/data/academic.json`. The `publications` array holds journal papers, conference papers, preprints, posters, talks, and seminars. Replace the sample with verified information; duplicate its object to add another entry.

This template is **illustrative only**. Replace every placeholder before setting `placeholder` to `false`:

```json
{
  "id": "your-unique-short-id",
  "type": "journal",
  "title": "Replace with the actual publication title",
  "authors": ["Your exact profile name", "Other actual author"],
  "venue": "Actual venue",
  "date": "2026-01-01",
  "status": "Published",
  "placeholder": true,
  "featured": true,
  "themes": ["reservoir", "forecasting"],
  "doi": "",
  "arxiv": "",
  "pdf": "",
  "code": "",
  "slides": "",
  "bibtex": ""
}
```

- Use a unique lowercase `id` containing letters, numbers, and hyphens. It becomes a link anchor.
- Valid types: `journal`, `conference`, `preprint`, `poster`, `talk`, `seminar`.
- Use a real `YYYY-MM-DD` date. Do not guess missing dates or metadata.
- `placeholder: true` shows a sample label and **excludes the entry from the CV**. Change to `false` only after verifying the full record.
- `featured: true` selects it for the homepage.
- Theme IDs: `reservoir`, `dynamics`, `networks`, `forecasting`. Matching records appear on the Research page.
- Author highlighting uses an exact match with `name` in `profile.json`.
- DOI: identifier only, such as `10.1234/example` (illustrative, not an actual citation). arXiv: identifier only, without a URL.
- `pdf`, `code`, and `slides`: a full HTTP(S) URL or a local path such as `/papers/my-paper.pdf`. Keep missing links as `""`; do not create fake links.
- `bibtex`: paste a verified BibTeX entry, with JSON line breaks written as `\n` and internal quotes escaped as `\"`. Copy/download buttons appear only when nonempty and the record is real.

Commit this one file. The website and PDF both read it during the same build. Do not edit generated `cv.pdf` manually.

## 3. Publish a journal post

Use **Add file → Create new file**. Name it `src/content/journal/your-short-title.md`. Paste:

```markdown
---
title: "Your article title"
description: "A short, accurate summary."
date: 2026-01-01
category: Research Notes
tags: [mathematics, notes]
cover: /images/waves.svg
coverAlt: "An illustrated moon over ocean waves"
sample: false
draft: true
---

Your writing begins here.

## A section

Inline mathematics: $x_{t+1}=f(x_t)$.

Display mathematics:

$$
L=D-A
$$
```

Use your real publication date. Choose exactly one category: **Research Notes**, **Conferences & Travel**, **Mathematics**, **Life & Other Things**. Tags are free-form. Use triple backticks followed by `python`, `typescript`, or another language for code highlighting.

- Keep `draft: true` while writing: drafts do not receive routes, appear in listings, or enter RSS/sitemap.
- Change it to `false` when ready. Future dates are not a scheduling system: a non-draft post is immediately visible after deployment.
- Mark fictional or demonstration posts with `sample: true`. The two included articles are explicitly labeled samples; delete them when no longer needed.
- `cover` and `coverAlt` can be omitted together. For images, upload small optimized WebP/JPEG files to `public/images/`. Paths omit `public`: `/images/my-cover.webp`.
- New posts are listed and added to RSS automatically. Rename a post file only if you also intend to change its URL and update old links.

## 7. Regenerate the CV
